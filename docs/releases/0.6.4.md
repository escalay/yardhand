## Apps' sign-ins run on the kit's newer OAuth server

Yardhand's built-in kit moves from 1.7.0 to 1.29.0. Apps you signed in before the update (claude.ai, ChatGPT, Claude
Code, Cursor) keep working: their sign-ins refresh as before and are not asked to connect again. What you may notice:

- **A refresh token sent twice signs the app out.** An app that sends a refresh token it already used (a retry after
  a lost answer, two refreshes sent at once, or someone replaying a stolen one) ends that whole sign-in: every token
  from it stops at once, even the one the first refresh just got, and the app must connect again. Before, only the
  repeated request was refused. The same holds for a sign-in code sent twice.
- **Approving must happen in the browser that opened the page.** The approval page at `/oauth/authorize` now sets a
  short-lived cookie, and the Allow button works only with it. An approval page left open across the update says
  "This approval expired" once: start again from the app. Scripts that post an approval by hand must load the page
  first and send its cookie back with `Sec-Fetch-Site: same-origin`.
- **The approval page says more.** It names the address the app asked for, and says "an app on this computer" when
  the app returns to this machine. An app whose registration Yardhand no longer knows is told to remove the
  connection and add it again.
- **An app that registered but never signed in is forgotten after a week.** It registers again by itself when it
  next connects. Apps that signed in keep their registration for a year, as before.
- **Devices can ask for a sign-in code** (RFC 8628). `POST /oauth/device_authorization` is new and open to anyone, as
  `/oauth/register` is, and the sign-in metadata names it (`device_authorization_endpoint`). Approving one at
  `/oauth/device` still needs Cloudflare Access in front, as `/oauth/claim` does: your Yardhand session approves only
  at `/oauth/authorize`.
- **The sign-in metadata and `/auth.md` are no longer cached** (`Cache-Control: no-store`), so an app fetches them once
  more per connection.
- **An `Idempotency-Key` no longer repeats a refusal.** A request refused (4xx) or failed (5xx) with an
  `Idempotency-Key` runs again when it is sent again with the same key; only a success is kept and replayed for a day.
  So a key that had ended and was extended needs no new `Idempotency-Key` to retry.
- **For tools reading Yardhand's tool lists.** Each of Yardhand's own MCP tools but `call_tool` names its route under
  `api-kit/route` in its `_meta` (before, `agent-api-kit/route`), beside two new keys: `api-kit/cli` (its command-line
  name) and `api-kit/tools-hash` (a hash of Yardhand's own tools and resources only: adding or removing a pin, or a
  pack's tool, leaves it as it was). Pinned tools and a pack's tools carry none of the three. Yardhand reads any
  `<vendor>/route` key from its upstreams, so upstreams on either key work as before.
- **Smaller wording.** `/openapi.json`'s write scope reads "Make changes" (it named an example before), and a 401
  over OAuth names `scope="read write"`.

Nothing to do by hand: no setting and no data change.

## Apps signed in by OAuth are told apart by their sign-in

Apps signed in by OAuth (claude.ai, ChatGPT, Claude Code, Cursor) are now told apart by their sign-in, not by the name
they gave. What you may notice:

- **Each existing one carries on as it was.** The first start of this version maps every sign-in made before it to the
  agent it used, once, so its pins, allowlist, pack and end date stay. Several sign-ins that gave the same name keep
  sharing that one agent, as before; one that gave the name of an agent you revoked is ended at that start.
- **An agent you approved with a claim code before the update** (one that registered at `/agent/identity`, not an
  app signed in at `/oauth/authorize`) works until its last token runs out, within the hour. Its identity assertion
  is no longer taken, so it then registers again and asks you for a new code. One you approved that had not yet
  picked up its approval carries on as it was.
- **A new connection is a new agent**, made when you approve it, even when the app gives the same name as one you
  have. It starts as before: can change things, every connection. The Agents page shows its OAuth client id under its
  name, to tell same-named agents apart.
- **Revoking one ends its sign-ins at once**: its tokens stop working and its refresh tokens are refused, so the app
  must connect again (before, its tokens were refused by the gateway but stayed valid at the sign-in). The app's
  registration stays, so connecting again needs no new registration.
- **A sign-in the gateway doesn't know is asked to connect again**: a 401 "This sign-in is not known here: connect
  again", where before an agent was made for it on first use.

Nothing to do by hand: the mapping runs by itself, before the gateway answers its first request.
