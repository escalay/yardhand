## Keys that last 30 days, and endings that say what to do

- **One thing to check: a script or monitor that reads an expired key's refusal.** A pack key that ended is now told `Your access to <pack> ended on <21 Dec 2026>. Ask the owner for a new invite.`, and a key without a pack `This key expired on <21 Dec 2026>: the owner can issue a new one in /app.` Both read `This key expired at <time>` before, so anything matching that text must match the new one. The status is still 403, and the day is the UTC day.
- **A key can last 30 days.** `POST /api/clients` takes `expiresIn: "30d"`, beside 8 hours, a day, a week and never.
- **A key's end can be moved.** `PATCH /api/clients/{id}` with `expiresIn` sets it to 7 days, 30 days or never, counted from today (the button for it comes with People on the pack page). A key that already ended works again with the same key, so its holder changes nothing; a key that leaked before it ended works again too. A revoked key does not come back, and a pack key whose packs were all removed is refused unless the same request gives it a pack: extended, it would open nothing. One thing its holder may meet: a request that was refused with an `Idempotency-Key` while the key had ended keeps answering that refusal for a day, so a script that keeps one `Idempotency-Key` per job sends it again with a new one.
- **Over MCP an ended key connects and is told why.** At a pack's address (`/p/<pack>/mcp`, `/mcp/p/<pack>`) it was refused while connecting, which most apps show as a bare failure. It now connects, reads the sentence above as the server's instructions and gets it from every tool. It is shown nothing of the pack: only the gateway's own tools (`search_tools`, `call_tool` and the others), under the name Yardhand. Plain `/mcp`, where an ended key already connected, says the same. A monitor that took a failed connection for an ended key must read the instructions or a tool's answer instead.
- **Looking as someone whose access ended says what to do.** `GET /api/tools?as=<client>` for an ended client still answers 409, now with whose access ended, to which pack, on which day, and the request that extends it.
- **For scripts.** A new key can say where it will be pasted: `app` on `POST /api/clients` (`claude-code`, `cursor`, `codex`, `curl` or `typescript`). It is returned on the client and in `GET /api/config`, null when not said.

Nothing to do by hand: the clients table gains one column by itself.

## A pack can be renamed, and its old address keeps answering

- **A pack can be renamed.** Edit on its page has a Name field, and `PATCH /api/packs/{name}` takes `name`. Its address moves to `/p/<new>/`, and setup handed out from then on says the new address.
- **Nobody has to change their setup.** If the pack has a key that is not revoked when it is renamed, its old address keeps working: `/p/<old>/mcp`, `/p/<old>/api`, `/mcp/p/<old>` and the `x-gateway-pack` header are served as before, with no redirect to follow, and the links in an answer are under the new address. The pack's own pages (`/p/<old>/docs`, `/p/<old>/llms.txt`, `/p/<old>/openapi.json`) answer 308 to the same page at the new address. A key that ended counts: extend it and it works at the address it was set up with.
- **An old name stays the pack's until you free it.** No other pack can take it, by making one, renaming one or importing a config: each says which pack the name still leads to. `GET /api/packs/{name}` lists a pack's old names as `formerNames`, each with how many of its working keys last connected there. `DELETE /api/packs/{name}/names/{old}` frees one: anyone still set up with that address is refused from then on. Removing the pack frees them all. A pack that had no key when it was renamed, or only revoked ones, keeps no old name.
- **An old name says nothing to a key that does not open the pack.** It is refused there by the name it asked for, exactly as for a name that never existed.
- **Your own routes say where a pack went.** `GET /api/packs/<old>`, `pack=<old>` on the call log, the search log, the stats and the tools list, and `pack` on a new key now answer `No pack <old>: it was renamed to <new>. GET /api/packs/<new>.`
- **For scripts.** A script that addresses a pack by name in the owner's routes (`/api/packs/{name}`, `?pack=`) must use the new name after a rename; only a pack's own address keeps the old one. `PATCH /api/packs/{name}` can now answer 409 (a name another pack has, or that still leads to one). A client made or changed with several packs that are not there is told one sentence per pack, where it was one sentence with the names joined by commas.

Nothing to do by hand: one table and two columns are added by themselves.

## A pack tool's input can have a default, and packs have variables

- **Three ways to fill an input.** Each input of a pack tool is now Fixed, a Default, or left to the agent. Fixed is what it was: the pack fills it on every call and its keys never see it. A Default is shown to the pack's keys with the pack's value, filled in when a call leaves it out, and the agent may send another value instead. Every other input is the agent's, as before.
- **Variables.** A pack has named values, set with `PUT /api/packs/{name}/variables` and written `{{name}}` in a fixed or default value: change the variable once and every tool that writes it follows. A value that is one variable and nothing else keeps its type, so `{{since_days}}` set to `7` is sent as the number 7.
- **Nothing changes for the packs you have.** A `{{word}}` in a value is read as a variable only once the pack has a variable of that name. Until then it is sent exactly as written, as before.
- **Values are checked when you save them.** A fixed or default value is checked against the tool's live input schema with the variables filled in, and so is a variable's new value against every input that uses it. Where the gateway can't read an input's schema, the pack says the value was not checked instead of saying it fits. A variable can't be removed while a value still writes it.
- **A value that stops fitting is flagged.** When a server drops an input a pack fills, or no longer takes its value, the tool is flagged on the pack, in Reviews and on Home, for defaults as for fixed inputs. Until you change it, a fixed value the tool refuses fails every call, and a default it refuses fails the calls that leave that input out. A value for an input the server dropped is still sent, and fails only if the server refuses inputs it doesn't know. A flag never blocks another change to the pack: only a save that sends the flagged value again is refused.
- **A pack tool can't be named like one of the connection's own tools.** A new alias that is `search_tools`, `describe_tool`, `call_tool`, `get_result`, `list_upstreams`, `read_resource` or `get_playbook` is refused, when a tool is added and when it is renamed. A pack that already has such a name keeps working as it did, and a config import still takes it.
- **In the app.** A pack's Tools tab opens with a Variables card: add a variable as text, a number or yes/no, change it, or remove it once no value writes it. **Name & inputs** on a tool now lists every input with who fills it (Fixed, Default or Agent decides), a button that writes one of the pack's variables into the value, what the value is sent as, and whether every stored value fits the tool's current schema. A refused save says why beside the input or the variable it is about. The line under a tool shows what it fixes and what it defaults, and Reviews says what no longer fits and sends you to the pack to change the value.
- **For scripts.** `GET /api/packs/{name}` gains `variables` and `findings`, and each of its tools `defaults` and `inputs` (one per input of the live tool: its mode, the value as written and filled in, what is wrong with it, and `unchecked` when the value could not be checked). `PATCH /api/packs/{name}/tools/{tool}` and `add.tools[]` on `PATCH /api/packs/{name}` take `defaults`. A refused save now starts `Not saved:` where it said `Fixed inputs don't fit:`, says which of the pack's tools each problem is in, and lists each problem with its place under `errors`. `GET /api/packs/flags` reports a default the tool dropped as `was: "defaults <input>"`. `GET /api/config` carries each pack's `variables` and each tool's `defaults`, and `POST /api/config` takes them.

Nothing to do by hand: no new setting, and the new column and table are added by themselves.
