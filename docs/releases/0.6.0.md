## Keys that last 30 days, and endings that say what to do

- **One thing to check: a script or monitor that reads an expired key's refusal.** A pack key that ended is now told `Your access to <pack> ended on <21 Dec 2026>. Ask the owner for a new invite.`, and a key without a pack `This key expired on <21 Dec 2026>: the owner can issue a new one in /app.` Both read `This key expired at <time>` before, so anything matching that text must match the new one. The status is still 403, and the day is the UTC day.
- **A key can last 30 days.** `POST /api/clients` takes `expiresIn: "30d"`, beside 8 hours, a day, a week and never.
- **A key's end can be moved.** `PATCH /api/clients/{id}` with `expiresIn` sets it to 7 days, 30 days or never, counted from today (the button for it comes with People on the pack page). A key that already ended works again with the same key, so its holder changes nothing; a key that leaked before it ended works again too. A revoked key does not come back. One thing its holder may meet: a request that was refused with an `Idempotency-Key` while the key had ended keeps answering that refusal for a day, so a script that keeps one `Idempotency-Key` per job sends it again with a new one.
- **Over MCP an ended key connects and is told why.** At a pack's address (`/p/<pack>/mcp`, `/mcp/p/<pack>`) it was refused while connecting, which most apps show as a bare failure. It now connects, reads the sentence above as the server's instructions and gets it from every tool. It is shown nothing of the pack: only the gateway's own tools (`search_tools`, `call_tool` and the others), under the name Yardhand. Plain `/mcp`, where an ended key already connected, says the same. A monitor that took a failed connection for an ended key must read the instructions or a tool's answer instead.
- **Looking as someone whose access ended says what to do.** `GET /api/tools?as=<client>` for an ended client still answers 409, now with whose access ended, to which pack, on which day, and the request that extends it.
- **For scripts.** A new key can say where it will be pasted: `app` on `POST /api/clients` (`claude-code`, `cursor`, `codex`, `curl` or `typescript`). It is returned on the client and in `GET /api/config`, null when not said.

Nothing to do by hand: the clients table gains one column by itself.

## A pack can be renamed, and its old address keeps answering

- **A pack can be renamed.** Edit on its page has a Name field, and `PATCH /api/packs/{name}` takes `name`. Its address moves to `/p/<new>/`, and setup handed out from then on says the new address.
- **Nobody has to change their setup.** If the pack has a key that is not revoked when it is renamed, its old address keeps working: `/p/<old>/mcp`, `/p/<old>/api`, `/mcp/p/<old>` and the `x-gateway-pack` header are served as before, with no redirect to follow, and the links in an answer are under the new address. The pack's own pages (`/p/<old>/docs`, `/p/<old>/llms.txt`, `/p/<old>/openapi.json`) answer 308 to the same page at the new address. A key that ended counts: extend it and it works at the address it was set up with.
- **An old name stays the pack's until you free it.** No other pack can take it, by making one, renaming one or importing a config: each says which pack the name still leads to. `GET /api/packs/{name}` lists a pack's old names as `formerNames`, each with how many of its people last connected there (someone whose access ended in the last 30 days counts: Extend brings their setup back). `DELETE /api/packs/{name}/names/{old}` frees one: anyone still set up with that address is refused from then on. Removing the pack frees them all. A pack that had no key when it was renamed, or only revoked ones, keeps no old name.
- **An old name says nothing to a key that does not open the pack.** It is refused there by the name it asked for, exactly as for a name that never existed.
- **Your own routes say where a pack went.** `GET /api/packs/<old>`, `pack=<old>` on the call log, the search log, the stats and the tools list, and `pack` on a new key now answer `No pack <old>: it was renamed to <new>. GET /api/packs/<new>.`
- **For scripts.** A script that addresses a pack by name in the owner's routes (`/api/packs/{name}`, `?pack=`) must use the new name after a rename; only a pack's own address keeps the old one. `PATCH /api/packs/{name}` can now answer 409 (a name another pack has, or that still leads to one). A client made or changed with several packs that are not there is told one sentence per pack, where it was one sentence with the names joined by commas.

Nothing to do by hand: one table and two columns are added by themselves.

## Share a pack with one person, and see who has it

- **One request shares a pack.** `POST /api/packs/{name}/people` with `name` (who it is for) makes that person's key for that pack alone: read only and for 30 days, unless you send `scope: "write"` or another `expiresIn` (`8h`, `1d`, `7d`, `30d` or `never`). A pack that holds no tools answers 409: add tools first.
- **The answer is a message ready to send.** `message` says what the pack is, what the person can do with it and until which day, then the setup for their app with the key already in it. Say the app with `app` (`claude-code`, `cursor`, `codex`, `curl` or `typescript`); left out, the message gives the pack's address and the bearer line. The address in it is the one set in `PUBLIC_HOST`, so the person can reach it even when you asked over the LAN or localhost; with `PUBLIC_HOST` unset it is the address your request came by. claude.ai is not one of them: it signs in and takes no key. The key (`key`, and inside `message`) is shown this once.
- **A pack lists its people.** `GET /api/packs/{name}/people` has one row per client that opens the pack: the app, read or write, when it ends, the last call and the calls in 7 days, `ending` in the last three days, the other packs the same key opens, and the old address it still connects at after a rename. Extend and Revoke are the client's own routes (`PATCH` and `DELETE /api/clients/{id}`).
- **Someone whose access ended stays listed for 30 days**, marked `ended`, so it can be extended; after that, and once revoked, they are not listed. `GET /api/packs/{name}` counts the same people: `ending`, `ended`, and `keys + ended` is the number the list holds.
- **A key answered under an `Idempotency-Key` is no longer readable in the database.** A request sent with an `Idempotency-Key` has its answer kept for a day, to answer a retry. That answer was kept as it was, so a new key (`POST /api/clients`, a share, the claim of a new instance) or a sign-in cookie lay readable in the database and in the daily backups made that day. Every kept answer is now sealed with the master key, and the ones already kept are sealed at the first start of this version. A retry is answered as before. Backups made before the update (kept 7 days) still hold what they held: if you made a key with an `Idempotency-Key` in the week before updating and a backup may have left your hands, revoke that key and share again.
- **For scripts.** A key that opens several packs is a person in each: its calls are counted in all of them, and an Extend or a revoke applies to all (`otherPacks` names them). A key made with `POST /api/clients` and a pack is listed like one made by sharing. A name is one line: the spaces around it are dropped and a line break answers 400, when sharing and on `POST` and `PATCH /api/clients` alike, since the name is printed in the message, on Home and in the webhook's notice.

Nothing to do by hand, and no data changes.

## On a pack's page, People in place of Keys and Share in place of Give access

- **Share asks four things and hands you a message.** On a pack's page, Share opens a sheet: who the pack is for, which app they use (Claude Code, Cursor, Codex, a script, or not sure), what they can do (asked only when the pack holds tools that change things; read only unless you say otherwise) and for how long (7 days, 30 days unless you say otherwise, or until revoked). It ends on a message to send them, with the setup for their app and their key in it. The key is shown this once, and the sheet then waits for their first call.
- **People lists who has the pack.** One row per person: how they connect, what they can do, when it ends (marked in its last three days), their last call and their calls in 7 days, with Extend, Revoke and their Activity. Someone whose access ended stays listed for 30 days, and Extend makes the same key work again.
- **Old addresses are under People.** After a rename, each old address that still answers is listed with how many people still connect there, and each of those people's rows says so. Stop answering there frees the name: anyone still set up with it is refused from their next call.
- **Old links keep working.** `?tab=keys` opens People.
- **A key for several packs, or for a day or less, is still made under Agents.** The pack page's header no longer leads there; the foot of People does. Under Agents, the page of a pack key that ended points to its pack's People.

Nothing to do by hand.

## A nudge three days before someone's access to a pack ends

- **Home says whose access is about to end.** Three days before a person's access to a pack ends, Needs you names them, the pack and the day, and its Extend opens the pack's People. `GET /api/overview` has it as a nudge of kind `access_ending`. The day is the UTC day. A key that opens several packs is named with its default pack; Extend moves its end for all of them.
- **The Discord webhook says it too, once.** With `DISCORD_WEBHOOK_URL` set, the hourly job posts who is ending, each with the link to the pack's People and the request that extends them: the webhook now carries these beside review notices, and Settings calls the part Alerts on Discord. An end is said once; someone you extended is said again when that end comes near. Right after updating, everyone already in their last three days is posted once.
- **Notices no longer wait on a clean sync.** When a connection failed to sync, that hour's review notice was held back. Both notices are now sent either way; the sync job still shows as failed, with the connections that failed.
- **Keys given for three days or less are not announced.** They would be ending the moment they were made.

Nothing to do by hand.
