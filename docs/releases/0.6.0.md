## Keys that last 30 days, and endings that say what to do

- **One thing to check: a script or monitor that reads an expired key's refusal.** A pack key that ended is now told `Your access to <pack> ended on <21 Dec 2026>. Ask the owner for a new invite.`, and a key without a pack `This key expired on <21 Dec 2026>: the owner can issue a new one in /app.` Both read `This key expired at <time>` before, so anything matching that text must match the new one. The status is still 403, and the day is the UTC day.
- **A key can last 30 days.** `POST /api/clients` takes `expiresIn: "30d"`, beside 8 hours, a day, a week and never.
- **A key's end can be moved.** `PATCH /api/clients/{id}` with `expiresIn` sets it to 7 days, 30 days or never, counted from today (the button for it comes with People on the pack page). A key that already ended works again with the same key, so its holder changes nothing; a key that leaked before it ended works again too. A revoked key does not come back, and a pack key whose packs were all removed is refused unless the same request gives it a pack: extended, it would open nothing. One thing its holder may meet: a request that was refused with an `Idempotency-Key` while the key had ended keeps answering that refusal for a day, so a script that keeps one `Idempotency-Key` per job sends it again with a new one.
- **Over MCP an ended key connects and is told why.** At a pack's address (`/p/<pack>/mcp`, `/mcp/p/<pack>`) it was refused while connecting, which most apps show as a bare failure. It now connects, reads the sentence above as the server's instructions and gets it from every tool. It is shown nothing of the pack: only the gateway's own tools (`search_tools`, `call_tool` and the others), under the name Yardhand. Plain `/mcp`, where an ended key already connected, says the same. A monitor that took a failed connection for an ended key must read the instructions or a tool's answer instead.
- **Looking as someone whose access ended says what to do.** `GET /api/tools?as=<client>` for an ended client still answers 409, now with whose access ended, to which pack, on which day, and the request that extends it.
- **For scripts.** A new key can say where it will be pasted: `app` on `POST /api/clients` (`claude-code`, `cursor`, `codex`, `curl` or `typescript`). It is returned on the client and in `GET /api/config`, null when not said.

Nothing to do by hand: the clients table gains one column by itself.

## A pack can be renamed, and its old address keeps answering

- **A pack can be renamed.** Edit on its page has a Name field, and `PATCH /api/packs/{name}` takes `name`. Its address moves to `/p/<new>/`, and setup handed out from then on says the new address.
- **Nobody has to change their setup.** If the pack has a key that is not revoked when it is renamed, its old address keeps working: `/p/<old>/mcp`, `/p/<old>/api`, `/mcp/p/<old>` and the `x-gateway-pack` header are served as before, with no redirect to follow, and the links in an answer are under the new address. The pack's own pages (`/p/<old>/docs`, `/p/<old>/llms.txt`, `/p/<old>/openapi.json`) answer 308 to the same page at the new address. A key that ended counts: extend it and it works at the address it was set up with.
- **An old name stays the pack's until you free it.** No other pack can take it, by making one, renaming one or importing a config: each says which pack the name still leads to. `GET /api/packs/{name}` lists a pack's old names as `formerNames`, each with how many of its working keys last connected there. `DELETE /api/packs/{name}/names/{old}` frees one: anyone still set up with that address is refused from then on. Removing the pack frees them all. A pack that had no key when it was renamed, or only revoked ones, keeps no old name.
- **An old name says nothing to a key that does not open the pack.** It is refused there by the name it asked for, exactly as for a name that never existed.
- **Your own routes say where a pack went.** `GET /api/packs/<old>`, `pack=<old>` on the call log, the search log, the stats and the tools list, and `pack` on a new key now answer `No pack <old>: it was renamed to <new>. GET /api/packs/<new>.`
- **For scripts.** A script that addresses a pack by name in the owner's routes (`/api/packs/{name}`, `?pack=`) must use the new name after a rename; only a pack's own address keeps the old one. `PATCH /api/packs/{name}` can now answer 409 (a name another pack has, or that still leads to one). A client made or changed with several packs that are not there is told one sentence per pack, where it was one sentence with the names joined by commas.

Nothing to do by hand: one table and two columns are added by themselves.

## A pack tool's input can have a default, and packs have variables

- **Three ways to fill an input.** Each input of a pack tool is now Fixed, a Default, or left to the agent. Fixed is what it was: the pack fills it on every call and its keys never see it. A Default is shown to the pack's keys with the pack's value, filled in when a call leaves it out, and the agent may send another value instead. Every other input is the agent's, as before.
- **Variables.** A pack has named values, set with `PUT /api/packs/{name}/variables` and written `{{name}}` in a fixed or default value: change the variable once and every tool that writes it follows. A value that is one variable and nothing else keeps its type, so `{{since_days}}` set to `7` is sent as the number 7.
- **Nothing changes for the packs you have.** A `{{word}}` in a value is read as a variable only once the pack has a variable of that name. Until then it is sent exactly as written, as before.
- **Values are checked when you save them.** A fixed or default value is checked against the tool's live input schema with the variables filled in, and so is a variable's new value against every input that uses it. Where the gateway can't read an input's schema, the pack says the value was not checked instead of saying it fits. A variable can't be removed while a value still writes it.
- **A value that stops fitting is flagged.** When a server drops an input a pack fills, or no longer takes its value, the tool is flagged on the pack, in Reviews and on Home, for defaults as for fixed inputs. Until you change it, a fixed value the tool refuses fails every call, and a default it refuses fails the calls that leave that input out. A value for an input the server dropped is still sent, and fails only if the server refuses inputs it doesn't know. A flag never blocks another change to the pack: only a save that sends the flagged value again is refused.
- **A pack tool can't be named like one of the connection's own tools.** A new alias that is `search_tools`, `describe_tool`, `call_tool`, `get_result`, `list_upstreams`, `read_resource` or `get_playbook` is refused, when a tool is added and when it is renamed. A pack that already has such a name keeps working as it did, and a config import still takes it.
- **In the app.** A pack's Tools tab opens with a Variables card: add a variable as text, a number or yes/no, change it, or remove it once no value writes it. **Name & inputs** on a tool now lists every input with who fills it (Fixed, Default or Agent decides), a button that writes one of the pack's variables into the value, what the value is sent as, and whether every stored value fits the tool's current schema. A refused save says why beside the input or the variable it is about. The line under a tool shows what it fixes and what it defaults, and Reviews says what no longer fits and sends you to the pack to change the value.
- **For scripts.** `GET /api/packs/{name}` gains `variables` and `findings`, and each of its tools `defaults` and `inputs` (one per input of the live tool: its mode, the value as written and filled in, what is wrong with it, and `unchecked` when the value could not be checked). `PATCH /api/packs/{name}/tools/{tool}` and `add.tools[]` on `PATCH /api/packs/{name}` take `defaults`. A refused save now starts `Not saved:` where it said `Fixed inputs don't fit:`, says which of the pack's tools each problem is in, and lists each problem with its place under `errors`. `GET /api/packs/flags` reports a default the tool dropped as `was: "defaults <input>"`. `GET /api/config` carries each pack's `variables` and each tool's `defaults`, and `POST /api/config` takes them.

Nothing to do by hand: no new setting, and the new column and table are added by themselves.

## Share a pack with one person, and see who has it

- **One request shares a pack.** `POST /api/packs/{name}/people` with `name` (who it is for) makes that person's key for that pack alone: read only and for 30 days, unless you send `scope: "write"` or another `expiresIn` (`8h`, `1d`, `7d`, `30d` or `never`). A pack that holds no tools answers 409: add tools first.
- **The answer is a message ready to send.** `message` says what the pack is, what the person can do with it and until which day, then the setup for their app with the key already in it. Say the app with `app` (`claude-code`, `cursor`, `codex`, `curl` or `typescript`); left out, the message gives the pack's address and the bearer line. The address in it is the one set in `PUBLIC_HOST`, so the person can reach it even when you asked over the LAN or localhost; with `PUBLIC_HOST` unset, or naming only the machine itself (the compose file's default is `http://localhost:<port>`), it is the address your request came by. claude.ai is not one of them: it signs in and takes no key. The key (`key`, and inside `message`) is shown this once.
- **A pack lists its people.** `GET /api/packs/{name}/people` has one row per client that opens the pack: the app, read or write, when it ends, the last call and the calls in 7 days, `ending` in the last three days, the other packs the same key opens, and the old address it still connects at after a rename. Extend and Revoke are the client's own routes (`PATCH` and `DELETE /api/clients/{id}`).
- **Someone whose access ended stays listed for 30 days**, marked `ended`, so it can be extended; after that, and once revoked, they are not listed. `GET /api/packs/{name}` counts the same people: `ending`, `ended`, and `keys + ended` is the number the list holds. Each of its `formerNames` now counts them too, where it counted only working keys: someone whose access ended still counts there, since Extend brings their setup back.
- **A key answered under an `Idempotency-Key` is no longer readable in the database.** A request sent with an `Idempotency-Key` has its answer kept for a day, to answer a retry. That answer was kept as it was, so a new key (`POST /api/clients`, a share, the claim of a new instance) or a sign-in cookie lay readable in the database and in the daily backups made that day. Every kept answer is now sealed with the master key, and the ones already kept are sealed at the first start of this version. A retry is answered as before. Backups made before the update (kept 7 days) still hold what they held: if you made a key with an `Idempotency-Key` in the week before updating and a backup may have left your hands, revoke that key and share again.
- **For scripts.** A key that opens several packs is a person in each: its calls are counted in all of them, and an Extend or a revoke applies to all (`otherPacks` names them). A key made with `POST /api/clients` and a pack is listed like one made by sharing. A name is one line: the spaces around it are dropped and a line break answers 400, when sharing and on `POST` and `PATCH /api/clients` alike, since the name is printed in the message, on Home and in the webhook's notice.

Nothing to do by hand, and no data changes.

## On a pack's page, People in place of Keys and Share in place of Give access

- **Share asks four things and hands you a message.** On a pack's page, Share opens a sheet: who the pack is for, which app they use (Claude Code, Cursor, Codex, a script, or not sure), what they can do (asked only when the pack holds tools that change things; read only unless you say otherwise) and for how long (7 days, 30 days unless you say otherwise, or until revoked). It ends on a message to send them, with the setup for their app and their key in it. The key is shown this once, and the sheet then waits for their first call.
- **People lists who has the pack.** One row per person: how they connect, what they can do, when it ends (marked in its last three days), their last call and their calls in 7 days, with Extend, Revoke and their Activity. Someone whose access ended stays listed for 30 days, and Extend makes the same key work again.
- **Old addresses are under People.** After a rename, each old address that still answers is listed with how many people still connect there, and each of those people's rows says so. Stop answering there frees the name: anyone still set up with it is refused from their next call.
- **Old links keep working.** `?tab=keys` opens People.
- **A key for several packs, or for a day or less, is still made under Agents.** The pack page's header no longer leads there; the foot of People does. Under Agents, the page of a pack key that ended points to its pack's People.

Nothing to do by hand.

## A nudge three days before someone's access to a pack ends

- **Home says whose access is about to end.** Three days before a person's access to a pack ends, Needs you names them, the pack and the day, and its Extend opens the pack's People. `GET /api/overview` has it as a nudge of kind `access_ending`. The day is the UTC day. A key that opens several packs is named with its default pack; Extend moves its end for all of them. Each line under Needs you now carries its mark: amber for access about to end and for reviews, red for a connection that fails.
- **The Discord webhook says it too, once.** With `DISCORD_WEBHOOK_URL` set, the hourly job posts who is ending, each with the link to the pack's People and the request that extends them: the webhook now carries these beside review notices, and Settings calls the part Alerts on Discord. An end is said once; someone you extended is said again when that end comes near. Right after updating, everyone already in their last three days is posted once.
- **Notices no longer wait on a clean sync.** When a connection failed to sync, that hour's review notice was held back. Both notices are now sent either way; the sync job still shows as failed, with the connections that failed.
- **Keys given for three days or less are not announced.** They would be ending the moment they were made.

Nothing to do by hand.

## A pack can hold playbooks and a skill written for it

- **A pack's keys get them at once.** What you write for a pack is served to its keys, and to no one else: see the next section.
- **Playbooks of a pack's own.** `POST /api/packs/{name}/playbooks` takes a name and Markdown. Front matter gives the title, the description and the arguments; the text writes an argument or one of the pack's variables as `{{name}}`, names the pack's tools in backticks by the names the pack calls them, and numbers its steps. `PUT` and `DELETE /api/packs/{name}/playbooks/{playbook}` change and remove one.
- **One skill per pack.** `PUT /api/packs/{name}/skill` takes the text of "Working with <title>", in six sections: What it is for, Which tool for which job, Values already set, Playbooks, Gotchas, What it can't do. The gateway writes the front matter and the heading itself, from the pack's name, title and what it is for, so front matter and a first `# ` heading you send are dropped.
- **Every save is checked.** Refused, with everything wrong listed: a tool in backticks that is not in the pack, or written by its own name where the pack gives it another; a `{{word}}` that is neither an argument nor a variable (in a text nothing is sent as written, unlike in a tool's value); front matter that can't be read, or an argument named like what every object already has (`constructor`). Every `{{word}}` in a playbook or the skill is read, inside fenced code blocks too, and there is no escape to keep one as written. Said, and saved anyway: a tool a read-only key can't run, a name that looks like a tool and is none, a `{{…}}` that is not written as a name (`{{Guest}}`, `{{guest-name}}`: nothing fills it in), a playbook past 12 steps, a section the skill lacks. `POST /api/packs/{name}/checks` runs the same checks on a draft and saves nothing.
- **Only a name in backticks is read as a tool.** A tool named in plain prose is not checked, and the text is not flagged when that tool changes.
- **Every version is kept.** Each changed save adds a version; `GET …/playbooks/{playbook}?version=<id>` and `GET …/skill?version=<id>` read an older text. Saving the same text adds none.
- **A text is flagged when a tool moves under it, never blocked by it.** Renaming a pack tool, removing it, or removing its connection goes through even when a playbook or the skill names it, and so does a server rewriting the tool. The text is then flagged on the pack, in Reviews and on Home, and agents keep it as it is, which can mean a playbook that names a tool the pack no longer has. Saving the text again clears the flag; while it still names a tool that has left, that save is refused and says what to write instead.
- **A variable a text writes can't be removed**, as for a value that writes it: `PUT /api/packs/{name}/variables` says which playbook, or the skill, still uses it.
- **In config exports.** Each pack in `GET /api/config` has `files`, a map of path to text: `playbooks/<name>.md` as written and `SKILL.md` as it is read, with its `{{name}}` left as written. They are plain Markdown files to keep in git. `POST /api/config` takes them after the pack's tools: a file that names a tool the pack does not have yet is skipped and comes in on the next import, and a text the pack already has is kept. A connection's playbook named like one the pack wrote itself is skipped too. Older versions are not exported.
- **For scripts.** `GET /api/packs/{name}` gains `ownPlaybooks`, `skill` and `counts.ownPlaybooks`, and its `findings` and `flags` count the pack's own texts too. `GET /api/packs/flags` gains the kinds `playbook` and `skill` and the field `item` (the playbook's name, or `SKILL.md`; null for a tool's own flags); for those kinds `tool` is the first name the text was written for that moved, and `_links.tool` is left out when that name no longer leads to a tool. `PATCH /api/packs/{name}` refuses to add a connection's playbook named like one of the pack's own.

Nothing to do by hand: two tables are added by themselves.

## A pack's keys get its playbooks and its skill

- **Playbooks, wherever a playbook is found.** A pack key lists the playbooks written for its pack first: as prompts (slash commands) over MCP, in `GET /api/playbooks`, and in the pack's instructions. Search suggests them, and `get_playbook` or `GET /api/playbooks/{name}/messages` fills one in with the agent's arguments and the pack's variables as they are at that moment. A required argument left out is a 400 that names it.
- **The skill, read first.** It is at `skill://<pack>/SKILL.md`: through `read_resource`, `GET /api/resources?uri=…`, and as a skill for apps that take the MCP Skills extension. A pack connection's instructions now open by sending the agent to it, and it is printed at the top of the pack's guide (`/p/<pack>/llms.txt`), under the pack's title.
- **Only the pack's own keys.** A key reads what was written for the pack its request is locked to, and nothing written for another: not by name, not in a list, a search or the guide. A key that opens two packs gets each pack's at that pack's address. Your own key gets them at a pack's address (`/p/<pack>/…`), as its keys do, and none at the root, where the authoring routes are.
- **Saved is served.** There is no review step for your own words: a save that passes its checks is what the pack's keys read next, and connected agents are told their prompts and resources changed. Changing a variable does the same.
- **After a rename.** A renamed pack's old address serves its playbooks and skill as before. The skill's own address follows the name the pack has now (`skill://<new>/SKILL.md`): an agent that kept the old one is told so and given the new address in the refusal, and in the instructions when it next connects.
- **A pack named like a connection.** If a pack has a skill and holds the manual of a connection with the pack's name, both would sit at `skill://<name>/SKILL.md`. The pack's skill takes that address; the manual leaves the Skills list for that pack's keys and is still read with `read_resource "gateway://u/<name>/manual"` and `GET /api/manuals/<name>`.
- **Counted on no connection.** A pack's own playbooks belong to none of its connections, so `list_upstreams` and `GET /api/upstreams` count as before. Their reads are in Activity with no connection beside them.
- **Agents can write a pack too.** `/llms.txt` has a new section, Writing a pack: the routes, a playbook's front matter by example, the skill's six sections, and what the checks refuse.
- **For scripts.** `upstream` on a playbook (`GET /api/playbooks`, `GET /api/playbooks/{name}`) and on `GET /api/resources` can now be null: a pack's own playbook or skill has no connection. A playbook gains `pack` (the pack that wrote it, else null), and `GET /api/me` gains `pack.ownPlaybooks` and `pack.skill`. `GET /api/playbooks?upstream=<id>` leaves a pack's own out. A `skill://` address nothing answers is now a 404 that says what there is, where it was a 400 asking for an upstream.

Nothing to do by hand.

## A pack's playbooks and its skill are written in the app

- **Playbooks & skill.** A pack's **Playbooks & manuals** tab is now **Playbooks & skill**. It opens on what is written for the pack, its own playbooks and its skill, above the playbooks and manuals it holds from its connections.
- **Write a playbook.** Give it a title: its name is made from the title, can be typed over, and can't be changed once saved. The text starts from a short example with front matter, one argument and three steps.
- **Write the skill.** It starts from the six sections, filled with what the pack already knows: what it is for, its tools by the names the pack calls them, its variables and the inputs it fills, and its playbooks. Read it and make it yours before saving: its agents are sent to it first.
- **Checked as you type.** Under the text are the checks a save runs, a moment after you stop typing: a tool that is not in the pack, a `{{word}}` nobody declared, front matter that can't be read. **Save** is held while one of them is a problem; what is only worth a look (a tool a read-only key can't run, a playbook past 12 steps, a missing section) never holds it. Beside the text is what agents read, with the pack's variables filled in as they are now.
- **Versions.** The editor lists every text a playbook or the skill had. Pick one to read it, and save it to serve it again.
- **Flags.** A playbook or skill written for a tool that has changed says what changed and offers to save it as it is, which clears the flag unless a tool it names is not live: that one stays flagged until the tool is back. One that names a tool that has left the pack, or been renamed in it, has to be edited first. The pack's header now says what there is to recheck by kind (`1 tool, 1 playbook and the skill to recheck`), the Tools tab and the Playbooks & skill tab each carry their own dot, and Reviews opens the pack on the tab the flag is on.
- **What its agents read first**, on the Overview, now names the skill and lists the pack's own playbooks first, as its keys are told.
- **Removing asks first.** Removing a playbook or the skill removes every version of it, and the pack's keys stop getting it at once.
- **Home's nudge reads differently.** It now says `3 things in your packs to recheck: tools they were set up for have changed or left their packs.` where it said `their servers changed the tools they were set up for`: a text is also flagged when its tool leaves the pack. A script that matches that sentence in `GET /api/overview` must match the new one.
- **One thing that reads oddly.** The Variables card says `Not used yet` for a variable that only a playbook or the skill writes: it lists the tools that write a variable, not the texts. Removing such a variable is still refused, and the refusal names the text.

Nothing to do by hand.

## Build and Refresh a pack with AI

- **A pack drafted from what it is for.** `POST /api/packs/{name}/builds` with `mode: "build"` and one to five example tasks drafts the pack's tools, each with why, a pack wording where a tool's own would mislead, variables, the inputs the pack fills (fixed or a default), a playbook for each task and the skill. `mode: "refresh"` does the same for a pack you have, and asks only for changes. It runs in the background: the answer is 202, and `GET /api/packs/{name}/builds/{id}` says where it is until its proposal is ready. One build runs at a time for a pack, and six may start an hour for one pack.
- **It tries each task first, with your accounts.** Before the proposal is shown, the model works through each example task with the drafted pack: tools that only read are really run with the accounts behind them, up to 6 calls a task, and those calls may cost on their own (a paid API, a quota). What they return is sent to the model's provider. A tool that changes things is never run, and neither is one you switched off: the model is told it was not run, and the proposal says so step by step. There is no way to build without this. The calls are in Activity under the door **Rehearsal**, with the call log, its export and the stats filter (`via=rehearsal`); Home, a tool's calls in 7 days, a connection's calls and the setup steps leave them out.
- **What a build sends.** The model's provider gets the pack's name, title and purpose, the example tasks, the tools it may pick (their descriptions and inputs), the manuals of their connections, and, while it rehearses, each drafted tool as the pack's keys see it: a default value is shown filled in with the pack's variables, a fixed one is not shown. Refresh also sends the pack as it is: its tools, wording, variables and the values it fills (an account label, say), and what is flagged on it.
- **$1 at most, with the estimate first.** `POST /api/packs/{name}/builds/estimate` says what a build is likely to cost on the model and the most real read calls its rehearsal may make, and asks nothing. A build estimated over $1.00 is refused before it starts (429 `spend_cap`: give fewer example tasks). A build that runs dearer than estimated stops before an ask would pass $1.00, or when the provider refuses for money (402 or 403), and keeps what it has: it says what it didn't get to, and what is there can still be accepted. The cost counted is the provider's own figure where it gives one (OpenRouter), else the model's list price; where neither is known, a build is held to 400,000 tokens instead and says `Cost not known for this provider`. The $1 is the model's only: a read tool that bills per call costs on top.
- **Nothing changes until you accept.** A proposal is a list of lines (a tool, its wording, one input, a variable, a playbook, the skill), each with before and after and the lines it needs: an input that writes `{{desk_name}}` needs the variable `desk_name`, and a playbook the tools it names. A tool that changes things starts unticked. `POST /api/packs/{name}/builds/{id}/accept` with the lines you want applies them through the same checks as any save, once, and only onto the pack as it was when the build started; `DELETE` discards it. Playbooks and the skill it writes keep their versions as any other, marked as written by `ai`. A tool it was not offered is never added, and is listed as left out.
- **Its own model.** Settings › AI has a third job, Build with AI, with a provider, address, key and model of its own (`PATCH /api/ai/builds`, `POST /api/ai/builds/test`), or in `.env` as `GATEWAY_AI_BUILDS_PROVIDER`, `GATEWAY_AI_BUILDS_BASE_URL`, `GATEWAY_AI_BUILDS_KEY` and `GATEWAY_AI_BUILDS_MODEL`. Each one left unset follows smart grouping's, so an instance with smart grouping set up builds with its writer model as it is; set a stronger model here for better playbooks without changing the one that names groups. A key it doesn't set is grouping's even when it sets an address of its own: set its key too when it runs elsewhere. `GET /api/ai` says where each of its settings comes from, `grouping` among them. The card for it in the app comes with the Build with AI screens.
- **Kept 30 days, sealed.** A proposal is kept sealed with the master key, as call payloads are, for 30 days, and goes with its pack. A build cut off by a restart reads as failed (`Interrupted`); the money it spent is spent.
- **For scripts.** `GET /api/packs/{name}` gains `build` (the newest build while it runs or waits). `via` on calls, call events, the call log's filter and `GET /api/overview/stats?via=` can be `rehearsal`; a caller can't send it (`x-gateway-via: rehearsal` is logged as `rest`). The usage report's call counts include rehearsal calls. `from` on a setting in `GET /api/ai` can be `grouping`.

Nothing to do by hand: one table is added by itself, and no setting is needed.
