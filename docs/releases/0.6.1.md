## Build with AI: proposals that keep what a pack has

- **A playbook is never named `task`, and never lands on one you have.** A build used to name a playbook `task` (then `task-2`) when the model's name was unusable, and a Refresh could then propose a `change` onto your own playbook of that name: accepting it replaced an unrelated playbook (its versions were kept). A playbook a build writes is now named for its task (`find-onboarding-screens`), a name the pack's own playbooks or its connections' playbooks already hold gets a number, and a playbook line is a change only when the model says it revises one of the pack's own playbooks by its name. That answer carries `"revises": true`; any other is an add under a free name.
- **A Refresh keeps the tools a pack has.** The model is told the tasks add to the pack. It may propose taking out only a tool that is not live or is switched off, and a removal it answers for any other tool is left out, under `skipped` with why. Taking a tool out is never ticked to begin with.
- **Every task gets its share of the tools looked at.** A build looks at 60 tools at most. It used to take them in order, the purpose's matches first, so on a gateway with a large connection a later task's tools could fall off. The tools the pack already holds now take half of them at most, so a Refresh of a large pack still looks at new ones. The purpose and each task take turns, and a task that names a connection by its id or its whole title (`find a note in the sample tools`) gets that connection's best matches right after its own best match. A tool switched off, or on a connection that is off, no longer takes a place.
- **A rehearsal no longer says a step happened when it didn't.** A tool that changes things is still never run, and the model was told to assume it worked, so an outcome could read "the announcement was scheduled". The model is now told nothing happened and to say what it would do. Each task in the proposal's `rehearsal` has `tried`: `false` when a step was handed a stand-in, was refused or failed, or none was taken, and the Proposal screen marks that task "Not tried". The stand-in's text changed: anything that matched `Assume it worked.` must match `so nothing happened.` instead.
- **The skill names only what the pack will have.** The skill's Playbooks section is written by the gateway: the pack's own playbooks, each with its description, then those it holds from its connections. Accept the skill with only some of those playbooks and the stored skill lists the ones the pack has after accept. The skill is asked to cover every tool of the pack, and a Refresh sends the skill as it is, to keep what it says of the tools that stay.
- **A pack of your own can start with the tools that change things ticked.** The Build and Refresh dialog has a box for it, "Tick tools that change things too", and `POST /api/packs/{name}/builds` and its estimate take it as `includeChanges: true`. The proposal then ticks the lines for tools that change things, and the playbooks and skill that need them. It is off unless sent, the estimate and the proposal say whether it was asked, and the rehearsal still never runs such a tool.

Nothing to do by hand: no setting and no data change. A proposal made before the update still reads and accepts as it did, with `tried` read from its steps, except that taking a tool out is no longer ticked in it.

## A playbook's arguments as their own query parameters

- **`?topic=tides` works.** `GET /api/playbooks/{name}/messages`, and the same under a pack's address (`/p/<pack>/api/playbooks/{name}/messages`), now takes each argument as its own query parameter, named as the playbook names it. `?arguments=<JSON>` works as before, and the two can be mixed.
- **A wrong name says what is allowed.** A query parameter the playbook doesn't take is a 400 that lists its arguments (`Unknown query parameter topik. Allowed here: arguments, topic.`), and an argument given twice, or both ways, is a 400 too. Before, every name but `arguments` was refused this way, the playbook's own arguments included.
- **A missing argument shows a use that works.** Over REST, the 400 for a required argument left out ends with the address to send: `Send each as its own query parameter: GET https://gw.example.com/p/<pack>/api/playbooks/<name>/messages?topic=<topic>`. The answer fills in the values the caller gave; the refused read in the log (`GET /api/calls`, the CSV) keeps `<name>` for each, so no value lands there. Over MCP it reads as before.
- **The guides say so.** `/llms.txt` and each pack's guide (`/p/<pack>/llms.txt`) show the form, and a pack's guide gives each playbook's address with its arguments.
- **For scripts.** A script that matched the exact text of the missing-argument 400 must allow the sentence now added at its end.

## Two more checks on a pack's skill

- **A playbook the skill names that the pack lacks is said.** A skill that names a playbook in its Playbooks section (in backticks, or as a list item's leading name), or anywhere a playbook of a connection the pack's tools or playbooks come from (`<upstream>-<prompt>`), that the pack does not have gets a warning, `unknown_playbook`, naming it. A playbook's argument, a tool's input, a variable or a tool is never taken for one. It is a warning: the skill is still saved.
- **A file's name is not taken for a tool's.** A backticked name such as `tokens.css` or `demo-effect.css` no longer gets the `unknown_name` warning. One named after a connection (`<upstream>.md`, `<upstream>.json`, `<upstream>.svg`) is a file's name, as in 0.6.0, and gets nothing. Only an ending 0.6.0 did not know as a file's (`<upstream>.log`, `<upstream>.lock`, `<upstream>.env`) is read as that connection's tool, which is an error, `not_in_pack`, when the pack does not have it.

## Search by meaning tries again by itself

- **A refresh that did not finish is tried again.** When the vectors for search by meaning were refreshed and the provider failed, or the key's spend cap or the refresh's own budget stopped it, nothing tried again until a sync changed tools, so tools approved meanwhile were found by their words only, for days. It now tries again after 1 minute, 5, 30, 2 hours, then every 6 hours, and the vectors made before it stopped are used at once.
- **A spend cap is tried on the same steps.** When the key's spend cap stopped it (OpenRouter's 402 or 403), it is tried again after 1 minute, 5, 30, 2 hours, then every 6 hours, as any other failure. A cap raised at the provider is picked up at the next of those tries, so within 6 hours; a restart, or a sync that changes tools, tries at once.
- **Settings › AI says when tools have no vector.** The search card says how many tools search finds by their words only, what stopped the last refresh and when it tries again. `GET /api/ai` has it as `vectors` on the `search` job (null for the other jobs, and while search has no key).

Nothing to do by hand: a restart also refreshes them, as before.

## A group named after its connection stays as it is

- **No more "Weathers".** Grouping by rules made a group's title plural from its tools' noun, also when that noun was the connection's own name (`weather` → Weathers) or a word with no plural. It now keeps a connection's one-word name as it is, and words such as weather, data, metadata or feedback too.
- **A group already named so keeps its name.** Only new groupings are named this way: rename one under the connection's Groups. Group keys are unchanged.
